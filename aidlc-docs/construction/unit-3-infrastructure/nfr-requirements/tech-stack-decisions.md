# Tech Stack Decisions — unit-3-infrastructure

**Date**: 2026-03-25
**Stage**: NFR Requirements
**Traceability**: FR-5, FR-8; NFR-4, NFR-8; U3-NFR-1..8

## Decision summary

| Decision | Choice |
|---|---|
| IaC | CloudFormation (generated YAML), StackSets for org mode |
| Event capture | CloudTrail → EventBridge rule per engagement |
| Decoupling | SQS queue between EventBridge and Lambda (+ DLQ) |
| Alerting | SNS; central per-region topic in org mode |
| Config store | SSM Parameter Store, standard tier |
| Template authoring | Generated by JS modules from shared sources — no hand-written YAML |

## D-1: CloudFormation + StackSets (not CDK, not Terraform)

**Chosen because**:
- **Customer-ownable with zero toolchain**: the customer deploys with the AWS
  CLI/console they already have. CDK would require Node, `cdk bootstrap` in every
  account, and trust in a synthesized output; Terraform requires a state backend
  and a third-party toolchain — both are adoption walls for a solution whose
  installer is a generated shell script run by the customer.
- **Reviewable artifact**: security teams review the actual YAML that will
  deploy — nothing is synthesized after their review (supports US-7, US-18).
- **StackSets is the only org-native multi-account deployment primitive** with
  service-managed permissions, delegated admin, and AutoDeployment — the exact
  FR-8 feature set, with no infrastructure of ours in the loop (NFR-4).

**Consequence accepted**: CFN's 4096-byte parameter value ceiling bounds explicit
account lists (~270 accounts, U3-NFR-5) — documented, not circumvented.

## D-2: SQS between EventBridge and Lambda (not direct invocation)

EventBridge *can* target Lambda directly; we interpose SQS deliberately:

- **The retry problem is minutes-scale**: slow provisioners need 3–10 minutes to
  become taggable. EventBridge→Lambda retry semantics are not shaped for "retry
  every ~3 minutes, five times, then park for manual replay"; SQS visibility
  timeout × maxReceiveCount expresses exactly that budget (U3-NFR-2).
- **Durability boundary**: 14-day retention on queue and DLQ gives the recovery
  window a missed-tag business cannot do without (U3-NFR-1). A failed direct
  invocation's event is gone after EventBridge's retry window.
- **Backpressure for migration waves**: cutover bursts queue up instead of
  throttling Lambda; cost stays flat (per-message pricing, no always-on).
- **Cost**: SQS standard, no KMS on the main queue — cents at our volumes.

## D-3: SNS with central-per-region topics in org mode

- **One subscription point**: US-11/US-14 fail in practice if a team must
  subscribe to a topic in every account. The central topic
  `auto-map-tagger-alerts-central-<mpe>` lives in the management account.
- **Per region because CloudWatch requires it**: alarm actions publish only to
  same-region topics — a single global topic is not physically possible; hence
  one central topic per deployed region.
- **Access by org identity**: topic policy conditioned on `aws:SourceOrgID` —
  robust to account churn, no principal-list maintenance (R-8).
- **KMS**: customer-managed key or none — never `alias/aws/sns` (hard rule R-7:
  CloudWatch cannot publish through the AWS-managed key and fails silently).

## D-4: SSM Parameter Store for runtime config

- Standard-tier parameter: free (NFR-8), IAM-controllable, versioned, and
  writable by CFN `!Sub` so the stack remains the single writer (R-3).
- Rejected: DynamoDB (cost/surface for one JSON document), Lambda env vars
  (second config source; function update per scope change), AppConfig (heavier
  than one parameter warrants).

## D-5: Generated templates from JS modules

`template-main.js` / `template-org.js` assemble YAML from the unit-4 registry,
`constants.js`, and the embedded unit-2 handler. One source feeds both
distribution artifacts (HTML-embedded and standalone YAML), making drift between
them structurally impossible, and lets event patterns and IAM be *derived* rather
than maintained (U3-NFR-9). Hand-editing generated output is prohibited; CI will
check artifact staleness.

## D-6: Staging S3 bucket for org mode

The inline Lambda handler pushes the template past the direct-submission body
limit; StackSets consumes the template from a namespaced staging bucket created
by the deploy script. Single-account mode stages the same way for uniformity.
Bucket is engagement-namespaced and region-qualified (R-1/R-2).
