# Security Test Instructions

**Stage**: Build and Test (Construction)
**Date**: 2026-03-27

## Purpose

The Security Baseline extension was enabled at Requirements Analysis, and the threat model is unusual: the configurator generates shell scripts that **customers run with their own AWS credentials**, and the runtime deploys IAM roles into **customer accounts**. Security testing therefore centers on: generated-script injection safety, least-privilege IAM, template hygiene, client-side XSS, and the hard "no outbound calls" constraint.

All checks below run in CI (`lint.yml` — hard gates unless marked advisory) and can be run locally.

## Test 1: Shell-Injection Lint on Generated Scripts (hard gate)

- **What**: Every user-supplied value interpolated into `deploy.sh` / `delete.sh` / `upgrade.sh` must be single-quote contained. A customer name like `x'; rm -rf ~; '` must land in the script as inert data.
- **Run**:
  ```bash
  python3 .github/scripts/lint_shell_injection.py
  ```
- **Expected**: exit 0. CI job: `shell-injection-guard`.
- **Also**: `tests/unit/deploy-script.test.js` and `delete-script.test.js` assert containment at the unit level with hostile inputs.

## Test 2: Bandit on the Lambda Handler (advisory)

- **What**: Static security analysis of `src/templates/lambda-handler.py` (the exact file embedded into the template).
- **Run**:
  ```bash
  pip install bandit && bandit -r src/templates/ .github/scripts/
  ```
- **Expected**: no high-severity findings. Advisory in CI (`bandit` job) — findings must be triaged, not ignored; suppressions require an inline justification.

## Test 3: cfn-nag / cfn-guard / cfn-lint on the Template

- **What**: CloudFormation hygiene on the built `configurator.yaml`: no wildcard principals, encryption settings, no insecure defaults.
- **Run**:
  ```bash
  npm run build:yaml
  cfn-lint configurator.yaml                     # hard gate (cfn-lint job)
  cfn_nag_scan --input-path configurator.yaml    # advisory (cfn-nag job)
  cfn-guard validate -d configurator.yaml -r <ruleset>   # advisory (cfn-guard job)
  python3 .github/scripts/lint_cfn_correctness.py        # hard gate (cfn-correctness job)
  ```
- **Expected**: cfn-lint and cfn-correctness exit 0; nag/guard findings triaged with documented rationale for any accepted risk.

## Test 4: IAM Least-Privilege Completeness (hard gate)

- **What**: The Lambda role must grant exactly the tagging actions the covered services need — complete (no silent tag failures from missing permissions) and minimal (no broad wildcards). Policies are generated by `.github/scripts/generate_iam.py` from the service definitions, so the check is a parity audit in both directions.
- **Run**:
  ```bash
  python3 .github/scripts/generate_iam.py --check
  ```
- **Expected**: exit 0. CI job: `iam-completeness`. Adding a service definition without its `permissions` entry fails this gate.
- **Review point**: any diff that widens an IAM action beyond `<service>:Tag*`-class permissions needs explicit human review — the customer owns these roles under the Shared Responsibility Model.

## Test 5: XSS Review of Configurator Inputs

- **What**: The configurator renders user input (customer name, MPE ID, scope selections) back into the DOM in review tables and generated-script previews. All such sinks must escape HTML.
- **Run**: manual probe — open the built `configurator.html`, enter `<img src=x onerror=alert(1)>` and `"'><script>` in every free-text field, walk every wizard step and the review table.
- **Expected**: payloads render as inert text everywhere; no script execution. Unit tests assert the escaping helper is applied at each sink.
- **Note**: the configurator is a static client-side file with no secrets and no backend — the XSS risk is a partner pasting a hostile value from a customer document, so the bar is "all sinks escaped", not CSP theatrics.

## Test 6: No Outbound Calls from the Deployed Lambda (hard design constraint)

- **What**: The deployed solution makes no network calls out of the customer's account — no telemetry, no update checks, no phoning home. GitHub Releases is the only update channel *because* of this rule.
- **Run**:
  1. Static: grep the handler for HTTP clients and non-AWS endpoints:
     ```bash
     grep -nE "urllib|requests|http://|https://" src/templates/lambda-handler.py
     ```
     Expected hits: none beyond boto3's own internals (boto3 calls AWS service endpoints in-region only).
  2. Dynamic (in the E2E account): review VPC flow logs / CloudTrail for the Lambda role — only Tagging API, SQS, SSM, and CloudWatch calls should appear.
- **Expected**: zero non-AWS destinations. Any feature that would add an outbound call is a design change requiring explicit human sign-off, not a normal PR.

## Test 7: Data-Safety Rules (security-adjacent, non-negotiable)

- `delete.sh` must **never** remove `map-migrated` tags — guarded by `tests/unit/delete-script.test.js` and Integration Scenario 5. Never weaken these to make a change pass.
- Teardown preserves operational data (log groups keep explicit DeletionPolicy + retention).

## Reporting

- Run everything locally with: `npm test` + the commands above; CI runs all of it on every PR via `lint.yml` (14 jobs) and `build.yml`.
- **Report security issues via the AWS vulnerability reporting page, never a public GitHub issue** (see `CONTRIBUTING.md`).
- SCP constraints in the customer org can override anything the tagger tries to do — that is by design and documented in `docs/LIMITATIONS.md`, not a finding.
