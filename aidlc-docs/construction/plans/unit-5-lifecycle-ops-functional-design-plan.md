# Functional Design Plan — unit-5-lifecycle-ops

**Date**: 2026-03-25
**Phase**: CONSTRUCTION — Functional Design
**Unit**: unit-5-lifecycle-ops (Deployment lifecycle and day-2 operations)
**Inputs**: `aidlc-docs/inception/application-design/unit-of-work.md`, `unit-of-work-story-map.md`, `requirements.md`

## Unit Context

unit-5 will own the *content* of the generated lifecycle scripts — `deploy.sh`,
`upgrade.sh`, `delete.sh` — and the preflight suite that runs before any
mutation. The scripts are generated by unit-1's configurator (the generator
modules live in `src/js/deploy/`, `src/js/delete/`, `src/js/upgrade/`) and run
by the customer with their own credentials, which makes safety rules here
non-negotiable: delete must never touch tags (NFR-6), user values must be
injection-safe (NFR-7), and no state-mutating failure may be silenced.

**Stories**: US-5 (deploy org-wide), US-8 (upgrade in place), US-9 (delete
without losing credits), US-10 (preflight before mutation).
**Requirements**: FR-2, FR-8, FR-13, FR-14, FR-15; NFR-6, NFR-7.

## Design Questions

## Question 1
Which deployment target modes must `deploy.sh` support?

A) Org-wide StackSets only

B) Single-account stack only

C) Both — org-wide StackSets (AutoDeployment, service-managed permissions, delegated-admin supported) and single-account plain stack, chosen at configuration time, with identical runtime behavior

D) Other (please describe after [Answer]: tag below)

[Answer]: C — both modes (FR-8, US-5 AC-2). Org StackSets is the default posture
for MAP customers (tens–hundreds of accounts; AutoDeployment covers accounts
added later), but single-account customers exist and must not be forced through
StackSets ceremony. The mode is selected in the configurator; the generated
script contains only the chosen mode's path.

## Question 2
How should `delete.sh` guarantee it can never remove `map-migrated` tags?

A) A confirmation prompt warning the operator not to untag

B) Structural absence — the delete flow contains no untag/RemoveTags code path at all; teardown enumerates infrastructure resources only, and a regression test asserts no tag-removal API appears in generated output

C) Untag capability behind a `--force` flag

D) Other (please describe after [Answer]: tag below)

[Answer]: B — structural absence, guarded by a hard regression test (NFR-6,
US-9 AC-2). MAP credits are permanent and irreversible; a prompt or a flag is a
policy, but an absent code path is a guarantee. The delete flow's teardown
scope is a closed allowlist of solution infrastructure (stack/StackSet
instances, staging bucket, orphan-swept namespaced resources) — customer
resources are unreachable by construction.

## Question 3
What are the upgrade semantics for stack parameters?

A) Re-prompt the operator for every parameter on each upgrade

B) `UsePreviousValue=true` for every parameter that already exists in the deployed stack; newly added parameters fall through to their template defaults (which must therefore be safe)

C) Overwrite all parameters from the newly generated script's values

D) Other (please describe after [Answer]: tag below)

[Answer]: B (FR-13, US-8 AC-1). The deployed stack is the source of truth for
the customer's configured values; the upgrade must never silently revert them
(option C would). Corollary rule: any *new* template parameter must ship with a
safe default, or the release is classified full-redeploy rather than
upgrade-safe. Preflight refuses upgrade on stacks whose state or parameter
shape is incompatible (US-8 AC-2).

## Question 4
How strictly should preflight gate mutation?

A) Warnings only — report issues but proceed

B) Hard gate — all preflight checks (peer-tagger collision, scope intersection, IAM capability, stack state) run before ANY mutating call; any failure aborts with a named, explained refusal and zero side effects

C) Hard gate for IAM/stack-state, warning for scope overlap

D) Other (please describe after [Answer]: tag below)

[Answer]: B — hard gate, zero-side-effect refusal (FR-15, US-10). Scope overlap
is the most dangerous finding, not the least: two taggers with intersecting
scope mis-attribute credits between engagements, which is unrecoverable —
warning-and-proceed (A, C) turns a refusal into a broken half-deployment or a
credit-integrity incident. Every refusal names the conflicting engagement or
missing capability so the operator can act (US-10 AC-1).
